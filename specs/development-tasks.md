# Workshop Registration Development Tasks

These tasks are based on [workshop-registration.md](./workshop-registration.md) and [plan.md](./plan.md). File paths below are illustrative because the application structure and technology stack have not yet been established.

| Task | Requirement being implemented | Files likely to change | Acceptance criteria covered | Tests required |
|---|---|---|---|---|
| **0. Resolve open requirements** | Confirm workshop availability, participant identity/authentication, email normalization, cancellation authorization/deadline, API errors, and date/timezone behavior. | `specs/plan.md` if decisions need recording | None directly; clarifies implementation scope. | None. |
| **1. Add workshop and registration persistence** | Store workshops and registrations; enforce unique registrations per workshop/email and safe capacity limits. | Database migration/schema; workshop and registration models/repositories; persistence tests | Supports all three registration scenarios and FR-05/FR-06. | Verify schema constraints; test counting registrations and rejecting duplicate or over-capacity writes, including concurrent attempts. |
| **2. Implement workshop listing and availability API** | Return workshops with registered counts and remaining seats; define “available” according to Task 0. | Workshop API route/controller; workshop service; response types; API tests | FR-01, FR-06 | Verify available-workshop results and seat counts for empty, partially filled, and full workshops. |
| **3. Implement registration API and business rules** | Accept a registration; reject duplicates and full workshops; keep capacity correct under concurrent requests. | Registration API route/controller; registration service; request/response types; API/service tests | Successful registration, workshop full, duplicate registration; FR-02, FR-03, FR-04, FR-06 | Given capacity 20 and 15 registrations, assert success and 4 seats remain. Given 20 registrations, assert rejection with a response the UI can display as **“Workshop is full”**. For `john@college.edu`, assert a second registration for the same workshop is rejected. Test concurrent attempts for the last seat. |
| **4. Implement cancellation API** | Cancel an authorized registration and restore one available seat. | Registration API route/controller; registration service; cancellation tests | FR-05, FR-06; no cancellation acceptance scenario is specified | Verify cancellation removes the registration, increases remaining seats, and rejects invalid or unauthorized cancellation according to Task 0 decisions. |
| **5. Build workshop listing UI** | Display workshop details and remaining seats from the API. | Workshop list/page; workshop card; API client/types; UI tests | FR-01, FR-06 | Verify workshop details and correct remaining seats render, including updated counts after registration and cancellation. |
| **6. Build registration UI and connect it to the API** | Collect email, submit registration, and display success, validation, duplicate, and full-workshop outcomes. | Registration form; workshop detail/list integration; API client; UI tests | Successful registration, workshop full, duplicate registration; FR-02, FR-06 | Test successful submission and updated seat count; full-workshop message is exactly **“Workshop is full”**; duplicate rejection is communicated; invalid email is handled. |
| **7. Add cancellation UI and end-to-end coverage** | Let a participant cancel and see availability update. Verify the registration flow across UI, API, and persistence. | Cancellation control; registration UI state; end-to-end tests | FR-05, FR-06; cancellation behavior has no explicit acceptance scenario | Test cancel action and seat restoration; run end-to-end success, full, duplicate, and cancellation scenarios against the application. |

Tasks 1–4 form the backend foundation; the UI tasks depend on the corresponding APIs. The acceptance criteria do not specify the duplicate-registration message or cancellation flow details, so decide those in Task 0 before finalizing related UI behavior.
